## 2. 決策摘要

| 編號 | 決策 | 理由／對應 00 |
|---|---|---|
| 02-D01 | net 層提供統一的傳輸介面，有兩種實作：記憶體傳輸（單機和測試，M0）和 ENet（多人，M9）。上層程式只看得到介面。 | 落實 01-D03：單機和多人走同一條程式路徑（00-A04）。 |

| 02-D04 | 自訂二進位協定：小端序；一個封包可以裝多則訊息，每則有 ID 和長度。訊息目錄集中在 shared，寫明 ID、方向、頻道和欄位型別。 | 只有一個來源，編碼、解碼和驗證都照目錄。 |
| 02-D05 | 握手時比對協定版本和遊戲資料雜湊，不同就拒絕。改了訊息目錄就一定要改版本號，由指紋測試強制。 | 避免兩邊版本不同造成難查的錯誤。 |

| 02-D07 | 登出、斷線、重複登入照 RO。攻擊、施放技能或被打之後 10 秒內不能登出；這段時間內斷線的話，角色會在世界上多留 10 秒。重複登入時，新的登入被拒絕，舊的連線被踢掉。 | 00-S07。 |
| 02-D08 | 時間同步：每秒 Ping／Pong 一次，取最近 8 次裡往返最短的樣本來估算伺服器時鐘，並平滑調整。 | 事件播放和插值都要用同一個伺服器時間。 |

| 02-D10 | 伺服器每個 tick 給每位玩家 1 點輸入額度，最多存 4 點，處理一個輸入用掉 1 點。輸入沒送到時，角色在伺服器上停著等，不猜。 | 網路抖動可以補回來，但改過的客戶端不能加速。 |
| 02-D11 | 每個指令附上送出當下的輸入序號，伺服器處理到那一步才執行。伺服器強制改變角色位置時用「移動紀元」作廢舊的預測和輸入。 | 兩個頻道的到達順序不一定，要用序號對齊，角色才不會被拉回去。 |
| 02-D12 | 其他實體：每個 tick（30 Hz）送一份快照，只送跟「客戶端確認收到的那份快照」比起來有變動的實體；客戶端延遲 100 ms 做插值。 | 畫面平滑；掉包也不會讓實體停在錯的位置。 |
| 02-D13 | 事件每個 tick 打包送一次，附伺服器時間戳。其他實體的動作在插值時間軸上播放；自己的動作收到就播（跟 RO 一樣，不預測攻擊）。 | 動作、位置和傷害數字對得上。 |
| 02-D14 | 興趣範圍：50 m 內進入視野，超過 55 m 才離開。出現和消失的原因照 RO 分類。 | 3D 鏡頭看得比 RO 遠（列在待檢視）。 |
| 02-D15 | 點怪攻擊：客戶端自動走進射程後送出攻擊意圖。伺服器只在「角色靜止、目標在射程內、攻擊時間到」時揮擊；目標跑遠就通知客戶端再追。射程容差照 RO：目標移動中時多 1 格。 | 01 第 3.2 節。站著打、移動就取消，跟 RO 一致。 |
| 02-D16 | 換圖照 RO：伺服器先把角色移出舊地圖，客戶端載入完回報後，才放進新地圖。抵達後有 3 秒保護，移動、攻擊或使用技能就提早結束。 | 00-A06、00-S07。 |
| 02-D17 | 存檔只由伺服器寫，用 JSON 檔，先寫暫存檔再取代，並保留一份備份。時機：每 300 秒（每人錯開）、登出、關機、換圖。 | 照 RO 的自動存檔間隔；換圖時多存一次（列在待檢視）。 |
| 02-D18 | 帳號由管理指令建立。密碼用 PBKDF2-HMAC-SHA256，迭代 600,000 次，加隨機鹽。同一個 IP 在 5 分鐘內失敗 7 次，封鎖 5 分鐘。多人連線開 DTLS 加密。 | 個人自用，但伺服器可能放在網路上。 |
| 02-D19 | 部署：匯出 Linux 專用伺服器版本（不打包美術素材），包成 Docker 映像。設定用環境變數，資料放在 `/data` volume。容器的入口腳本把 SIGTERM 轉成正常關機。 | 00-A04。Godot 在 Linux 收到 SIGTERM 會直接結束，不會存檔。 |
| 02-D20 | 記憶體傳輸內建網路模擬（延遲、抖動、掉包、亂序）。整合測試在不同網路條件下跑；單機模式也可以用參數開啟。 | 不用等到 M9 才發現連線問題。 |
| 02-D21 | 規模：同時在線 20 人，一個伺服器程序承載所有地圖。模擬在單一執行緒；只有密碼雜湊、地圖載入和寫檔放到背景執行緒。 | 簡單、行為可預測，20 人的規模足夠。 |

## 3. 傳輸

### 3.1 傳輸介面

```text
     客戶端（GameClient）                    伺服器（GameServer）
            │                                        │
       傳輸介面                                  傳輸介面
            │                                        │
   單機：記憶體傳輸（同一個程序裡的佇列）◄──────────►
   多人：ENet（UDP）                     ◄──────────►

   兩種傳輸外面都可以再包一層「網路模擬」（第 14 節）
```

| 介面功能 | 說明 |
|---|---|
| 送出 | 指定對象和頻道，送出一包位元組 |
| 收取 | 取出這段時間發生的事件：連線、斷線（附原因）、收到封包（附來源和頻道） |
| 中斷連線 | 指定對象，附原因碼 |
| 統計 | 往返時間、掉包率、收送的位元組數 |

規則：
- 伺服器在每個 tick 開頭取出所有收到的封包；在 tick 結尾送出這個 tick 的事件和快照，並立刻送出（不等下一輪）。
- 客戶端每一幀取出收到的封包。
- 單機時也照樣編碼成位元組再解碼（01-D03）。

### 3.2 頻道

| 頻道 | 傳送方式 | 客戶端 → 伺服器 | 伺服器 → 客戶端 |
|---|---|---|---|
| 0 控制與事件 | 可靠、有序 | 握手、登入、指令（攻擊、技能、坐下等） | 握手結果、事件（出現、消失、戰鬥、數值、換圖等） |
| 1 即時 | 不可靠、只取最新（比較舊的封包晚到就丟掉） | 移動輸入、Ping | 快照、Pong |
| 2 聊天與大筆資料 | 可靠、有序 | 聊天 | 聊天、大筆資料（例如之後的物品清單） |

為什麼要分開：
- 可靠頻道只要掉一包，就要等重送，後面的封包都會被卡住。
- 即時資料晚到就沒有用了，所以放在不可靠頻道，掉了就等下一份。
- 聊天和大筆資料另外開一條頻道，不會卡住戰鬥事件。

記憶體傳輸也模擬這三種行為，所以單機和多人的程式完全一樣。

### 3.3 為什麼直接用 ENetConnection

計畫大綱原本寫的是「用 SceneMultiplayer 的原始位元組，握手用它的驗證回呼」。查過 Godot 4.7 的文件後，我改成建議直接用 ENetConnection：

| 比較項目 | SceneMultiplayer＋ENetMultiplayerPeer | ENetConnection（建議） |
|---|---|---|
| 握手 | 驗證回呼只存在 ENet 這條路。單機的記憶體傳輸要另寫一套握手，或者把記憶體傳輸做成 MultiplayerPeer 擴充 | 握手寫在我們自己的協定裡，記憶體傳輸和 ENet 共用（01-D03） |
| 頻道控制 | 可以指定傳送模式和頻道 | 直接指定每一包的頻道和旗標 |
| 連線統計 | 要再透過底層的 peer 取得 | 直接讀往返時間、掉包率 |
| 用不到的功能 | RPC、同步器、生成器都在。伺服器轉送（server_relay）預設開啟，會把其他客戶端的連線告訴每個客戶端，要記得關掉 | 沒有，攻擊面最小 |
| 要多寫的程式 | 少 | 多一個小類別，處理連線、斷線、收包事件 |

這是跟計畫大綱不同的地方，2026-10-09 你確認採用（第 20 節第 1 項）。

### 3.4 封包大小與頻寬

- **不可靠封包**：控制在約 1,200 位元組以內。ENet 預設的 MTU 是 1,392，還要扣掉加密的額外長度。超過的話，ENet 會把分片改用可靠方式送，失去不可靠的意義；所以太大的快照會拆成幾包，每包都能單獨解碼。
- **可靠封包**：ENet 會自動分片，但單包上限訂為 64 KB。
- **壓縮**：不開。封包很小，壓縮的效益低，而且兩邊的設定必須一致。

頻寬估算（快照每秒 30 份，每個有變動的實體約 20 位元組，加上 UDP 和 ENet 標頭）：

| 情況 | 視野內正在動的實體 | 每位玩家下行 | 20 人時伺服器的上傳量 |
|---|---|---|---|
| 安靜 | 5 | 約 45 kbps | 約 0.9 Mbps |
| 一般 | 20 | 約 115 kbps | 約 2.3 Mbps |
| 熱鬧 | 60 | 約 310 kbps | 約 6.2 Mbps |

- 每位玩家上行（移動輸入）約 20 kbps。
- 戰鬥事件會再多一點，但量很小。
- 家用光纖的上傳頻寬就足夠。

## 4. 協定

### 4.1 編碼規則

全部用小端序（Godot 的預設）。

| 型別 | 長度 | 用途 |
|---|---|---|
| u8、u16、u32 | 1、2、4 位元組 | 訊息 ID、旗標、序號、實體 ID、tick |
| i32 | 4 | 有正負的數值（例如 HP 變化） |
| u64 | 8 | 毫秒時間戳（從伺服器啟動起算，不會溢位） |
| f32 | 4 | 位置座標（公尺） |
| 角度 | 2（u16） | 面向和移動方向，0～65535 對應 0～360° |
| 布林 | 1 | — |
| 字串 | 2＋內容 | UTF-8，前面 2 位元組是長度；每個欄位都有長度上限 |
| 列表 | 2＋內容 | 前面 2 位元組是項目數量 |

### 4.2 封包與訊息

```text
封包 ＝ [封包標頭] ＋ 訊息 1 ＋ 訊息 2 ＋ …

封包標頭：只有伺服器送出的封包有，內容是 tick（u32）
訊息    ：訊息 ID（u16）＋ 長度（u16）＋ 欄位（依訊息目錄）
```

- 每則訊息都有長度，解碼器可以檢查邊界。長度跟欄位對不上，就整包丟掉。
- 訊息 ID 依類別分段：

| 範圍 | 類別 |
|---|---|
| 0x0001～0x00FF | 連線控制（握手、登入、時間同步、登出、踢出） |
| 0x0100～0x01FF | 世界與實體（換圖、出現、消失、快照、狀態） |
| 0x0200～0x02FF | 移動 |
| 0x0300～0x03FF | 戰鬥 |
| 0x0400～0x04FF | 技能與狀態效果 |
| 0x0500～0x05FF | 物品 |
| 0x0600～0x06FF | 聊天與社交 |
| 0x0F00～0x0FFF | 除錯（只在開發模式接受） |

- 訊息目錄的每一筆包含：英文名稱、ID、方向、頻道、欄位清單（名稱、型別、範圍或長度上限），以及從哪個里程碑開始使用。
- 一般訊息用依照目錄運作的通用編解碼。最頻繁的兩種（快照、移動輸入）另外手寫最佳化版本，測試時跟通用版本比對結果。

### 4.3 版本檢查

| 項目 | 內容 |
|---|---|
| 協定版本 | 一個整數，寫在 shared |
| 協定指紋 | 從訊息目錄算出的雜湊。測試裡記錄「版本號 → 指紋」，目錄改了版本號卻沒改，測試就失敗 |
| 遊戲資料雜湊 | `data/` 底下所有 JSON 依路徑排序後算 SHA-256。兩邊的資料表不同（例如只更新了一邊）時，握手就拒絕 |

單機時兩邊在同一個程序裡，一定相同；這兩項檢查主要是給 M9 的多人連線用。

### 4.4 驗證與防護

| 檢查 | 做法 |
|---|---|
| 長度 | 每則訊息的長度要跟欄位對得上；字串和列表不能超過上限 |
| 範圍 | 列舉值要在定義的範圍內；浮點數必須是有效數值（不能是 NaN 或無限大） |
| 連線狀態 | 每個連線狀態只接受特定的訊息（第 5.1 節），其他一律丟掉 |
| 頻率 | 每種訊息都有每秒上限，例如移動輸入 60 包、指令 20 個；超過的丟掉 |
| 封包大小 | 客戶端送來的封包：可靠頻道最多 4 KB，即時頻道最多 512 位元組 |
| 違規累計 | 被丟掉的封包都會記 log 並計數；10 秒內超過 20 次就斷線 |
| 遊戲規則 | 目標存不存在、看不看得到、射程、冷卻、SP 等，由各系統檢查（06、07） |

客戶端從來不送位置，只送輸入；移動速度由伺服器決定。所以改過的客戶端不能瞬移，也不能加速（第 7.2 節）。

### 4.5 訊息目錄

以下列出訊息種類和用途。欄位細節在實作時寫進訊息目錄；戰鬥、技能、物品相關的欄位由 06、07、10 決定。「開始」欄是預計開始使用的里程碑，以 11 為準。M0 的單機骨架就要能進入地圖並收到快照（01 第 17 節），所以進場相關的訊息從 M0 開始。

**客戶端 → 伺服器**

| 訊息 | 頻道 | 內容 | 開始 |
|---|---|---|---|
| Hello | 0 | 協定版本、遊戲資料雜湊 | M0 |
| Login | 0 | 帳號、密碼（單機用本機帳號） | M0 |
| SelectCharacter | 0 | 角色 ID（單機自動選唯一的角色） | M0 |
| MapLoaded | 0 | 地圖 ID，表示客戶端已經載入完成 | M0 |
| Ping | 1 | 客戶端時間 | M0 |
| MoveInput | 1 | 最近 4 步的輸入（序號、移動方向、面向、旗標）、移動紀元、收到的最新快照 tick | M1 |
| SitStand | 0 | 坐下或起身 | M3 |
| AttackStart | 0 | 目標、單次或連續 | M5 |
| AttackStop | 0 | — | M5 |
| Respawn | 0 | 死亡後回到儲存點 | M5 |
| PickUp | 0 | 掉落物 ID | M6 |
| UseSkill | 0 | 技能、等級、目標或地點 | M7 |
| Emote | 0 | 表情 ID | M8 |
| Logout | 0 | — | M9 |
| Chat | 2 | 文字 | 之後（未排） |
| DebugCommand | 0 | 除錯指令，例如傳送到某個地點（只在開發模式接受） | M1 |

所有指令（頻道 0 的遊戲訊息）都附上「送出當下最新的輸入序號」（第 7.3 節）。

**伺服器 → 客戶端**

| 訊息 | 頻道 | 內容 | 開始 |
|---|---|---|---|
| HelloResult | 0 | 成功或拒絕原因；伺服器設定（tick 頻率、快照頻率） | M0 |
| LoginResult | 0 | 成功或錯誤碼；角色清單 | M0 |
| Pong | 1 | 原本的客戶端時間、伺服器時間 | M0 |
| MapChange | 0 | 地圖 ID、位置、面向、移動紀元、自己的實體 ID 和外觀 | M0 |
| MapReady | 0 | 視野內的實體都送完了，客戶端可以淡入 | M0 |
| Snapshot | 1 | tick、伺服器時間、基準快照、自己的權威位置和已處理的輸入序號、有變動的實體 | M0 |
| EntityAppear | 0 | 實體的完整資料（類型、名稱、外觀、裝備外顯、位置、面向、移動速度、狀態）和出現原因 | M0 |
| EntityVanish | 0 | 實體 ID、消失原因 | M0 |
| PositionReset | 0 | 自己被強制移動：新位置、面向、移動紀元、原因 | M1 |
| SystemMessage | 0 | 文字 ID 和參數（玩家看到的文字放在資料表，03） | M1 |

## 5. 連線、登入與登出

### 5.1 連線狀態

```text
連線建立 ─► 握手 ─► 登入 ─► 選角 ─► 載入地圖 ─► 遊戲中
                                    ▲            │
                                    └── 換圖 ────┘
遊戲中 ─► 登出（RO 的 10 秒規則）─► 結束
任何狀態 ─► 斷線
```

| 狀態 | 伺服器接受的訊息 | 逾時 |
|---|---|---|
| 握手 | Hello | 10 秒內沒完成就斷線 |
| 登入 | Login | 60 秒 |
| 選角 | SelectCharacter、Ping | — |
| 載入地圖 | MapLoaded、Ping | 60 秒內沒回報就斷線，角色存在新地圖的位置 |
| 遊戲中 | 所有遊戲訊息 | — |

- 連線約 15 秒沒有回應就判定斷線（ENet 預設最長是 30 秒，這裡改短一點）。
- 同時連線的人數超過上限時，握手直接拒絕（原因：伺服器已滿）。

### 5.2 握手與登入

```text
客戶端                                     伺服器
連線建立 ──────────────────────────────────►
Hello（協定版本、資料雜湊）────────────────► 比對版本和雜湊
           ◄──────────────────────────────── HelloResult
Login（帳號、密碼）────────────────────────► 在背景執行緒驗證密碼
           ◄──────────────────────────────── LoginResult（角色清單）
SelectCharacter（角色）───────────────────► 讀取角色存檔
           ◄──────────────────────────────── MapChange
（接下來同第 11 節的換圖流程）
```

- **單機**：客戶端自動用本機帳號登入，自動選唯一的角色。伺服器只接受從記憶體傳輸來的本機帳號登入。
- **連線模式（M9）**：在登入畫面（10）輸入帳號和密碼。
- **拒絕原因**：版本不同、資料不同、伺服器已滿、帳號或密碼錯誤、IP 暫時封鎖、帳號仍在線上（第 5.4 節）、伺服器關閉中。玩家看到的文字放在資料表（03）。
- **登入位置**：照 RO，回到上次登出的位置。儲存點只用在死亡後復活（06）。01 第 5.2 節的寫法要配合修改，見第 19 節。

### 5.3 登出與斷線（照 RO）

| 情況 | 處理方式 |
|---|---|
| 主動登出 | 最後一次攻擊、施放技能或被打之後 10 秒內不能登出，會顯示提示。躲藏等隱身狀態中也不能登出。 |
| 斷線（連線中斷或強制關閉） | 如果還在上面那 10 秒內，角色會在世界上多留 10 秒（這段時間仍然可能被打），之後才移除；不在 10 秒內就立即移除。 |
| 角色移除時 | 存檔；其他人看到原因為「登出」的消失。 |
| 單機 | 關閉遊戲就是存檔後直接結束，本地伺服器跟著關閉，不套用 10 秒規則。 |

### 5.4 重複登入（照 RO）

- 帳號已經在線上時，新的登入會被拒絕（「伺服器仍記得你上次的登入」），同時伺服器把舊的連線踢掉。舊的客戶端會顯示「有人用這個帳號登入」。
- 舊角色依第 5.3 節的規則離開世界之後，再登入一次就可以了。

## 6. 時間同步

```text
客戶端在 c0 送出 Ping（c0）
伺服器回 Pong（c0, s）          s ＝ 伺服器的時間
客戶端在 c1 收到
  往返時間 ＝ c1 − c0
  時差樣本 ＝ s ＋ 往返時間 ÷ 2 − c1
```

- 連線後的前 2 秒，每 0.2 秒送一次 Ping，快速取得準確的時差；之後每秒一次。
- 保留最近 8 個樣本，用往返時間最短的那一個，因為它最不受網路排隊的影響。
- 估算的伺服器時間 ＝ 客戶端的單調時鐘 ＋ 時差。
- 時差有變動時：相差小於 250 ms 就用最多 ±10% 的速度慢慢追上，畫面不會跳；超過 250 ms（例如剛連線或長時間卡頓）就直接跳過去。
- Ping／Pong 走即時頻道。掉了只是少一個樣本，沒有影響。

## 7. 移動同步

### 7.1 自己的角色：預測與校正

```text
客戶端  產生輸入 #101 #102 #103 #104 #105   每一步先在本機算出位置，畫面立刻動
          │
          ▼  每 33 ms 送一包，附最近 4 步（掉包也不怕）
伺服器  處理到 #101，位置是 P101
          │
          ▼  快照：「已處理到 #101，位置 P101」
客戶端  跟自己記錄的第 #101 步位置比對
          相差 ≤ 1 cm：不處理
          相差 > 1 cm：從 P101 開始重播 #102～#105，畫面在 0.1 秒內平滑修正
          相差 > 2 m ：直接移過去
```

- 輸入的頻率跟伺服器 tick 一樣是每秒 30 次（01 第 6.3 節）。每一步用 shared 裡同一份移動程式計算，畫面在兩步之間插值。
- 每個輸入包含：序號、移動方向（世界座標的角度，沒有移動就標記為靜止）、面向、旗標（例如 09 若採用走路切換鍵）。
- 輸入和預測結果存進環狀緩衝，保留約 2 秒。
- 每包輸入也帶上「收到的最新快照 tick」，給伺服器當差量基準（第 7.6 節）。

### 7.2 伺服器處理輸入的規則

- 每位玩家有一個輸入佇列，依序號排序，重複的丟掉。
- 每個 tick 給 1 點額度，額度最多存 4 點；處理一個輸入用掉 1 點。
  - 網路抖動造成輸入晚到時，存下來的額度可以一次補處理幾步，最後的位置跟客戶端一致。
  - 平均每個 tick 最多只能處理 1 步，所以改過的客戶端送再多輸入也不會跑得比較快。
- 佇列超過 15 個（0.5 秒）就丟掉多的，客戶端之後會被校正。
- 輸入沒送到時，角色在伺服器上停著等，不猜測。

### 7.3 指令和輸入的先後順序

- 指令（攻擊、技能、坐下等）走可靠頻道，移動輸入走即時頻道，兩者到達伺服器的先後不一定。
- 每個指令都附上「送出當下最新的輸入序號」。伺服器要等那一步處理完才執行這個指令，最多等 200 ms；超過就直接執行（那個輸入可能掉了）。
- 這樣「停下來再坐下」這類操作，在伺服器上的順序就跟客戶端一樣，角色不會被拉回去。

### 7.4 強制位移

- 伺服器強制改變自己角色的位置時（換圖、同地圖傳送、擊退、技能造成的位移），移動紀元加 1，並送出 PositionReset（新位置、面向、紀元、原因）。
- 客戶端收到後，丟掉舊的預測，從新位置繼續。
- 伺服器忽略舊紀元的輸入，所以「傳送前送出的輸入」不會把角色帶走。
- 同一張地圖內的傳送不重新載入地圖；其他人看到「傳送」原因的消失，接著在新位置看到「新出現」。

### 7.5 不能移動的狀態

- 什麼時候不能移動由伺服器決定，例如坐下、詠唱、受擊硬直、攻擊動作中、死亡、載入中。規則在 06。
- 相關事件會帶「可以再移動的時間」，客戶端預測時照著停下來。猜錯的部分由第 7.1 節的校正修正。

### 7.6 其他實體：快照與插值

**快照內容：**
- 標頭：tick、伺服器時間、基準快照的 tick。
- 自己：已處理的最後一個輸入序號、移動紀元、權威位置和面向。這一段每份快照都有。
- 其他實體：只列出有變動的實體，每個包含實體 ID、變動旗標、位置、面向、移動狀態。

**差量的基準（避免掉包造成錯誤）：**
- 客戶端在每包輸入裡回報「收到的最新快照 tick」。
- 伺服器為每個客戶端保留最近 1 秒送出的快照內容。新快照跟「客戶端確認收到的那一份」比較，只送有變動的實體。
- 客戶端還沒確認過任何快照，或確認的那一份已經超過 1 秒，就送完整的快照。
- 客戶端也保留最近收到的快照，用「基準＋差量」重建出完整的狀態。
- 這樣即使某份快照掉了，下一份仍然會帶到所有跟客戶端已知狀態不同的實體。

**跟可靠頻道的先後：**
- 快照和事件都帶 tick。
- 實體還沒「出現」就先收到它的快照資料時，先暫存起來，等出現事件到了再套用。
- 已經消失的實體，比消失時間舊的快照資料直接丟掉。

**插值：**
- 畫面時間 ＝ 估算的伺服器時間 − 100 ms（約 3 份快照的量）。每個實體用畫面時間前後兩份快照做插值：位置線性插值、面向取最短的旋轉方向。
- 快照不夠時（掉包或延遲突然變大），照最後的速度往前推算最多 250 ms，之後停在原地等待；新的快照到了再平滑拉回。
- 插值延遲可以在設定裡調整。

## 8. 事件與播放時間

**送出：**
- 伺服器把同一個 tick 裡要給同一個客戶端的事件打包成一個可靠封包。
- 每個事件帶 tick，需要的話再帶毫秒時間戳，例如揮擊時間、命中時間。
- 數值在命中時間才生效（RO 的延遲傷害），細節在 06。

**播放時間軸：**

```text
伺服器時間 ───────────────────────────────────────────────►
                         T：怪物揮擊（伺服器決定）

客戶端畫面
  自己的角色：在「現在」（預測）
  其他實體  ：在「現在 − 100 ms」（插值）

→ 畫面時間走到 T 時才播放怪物的揮擊動作，跟它插值後的位置一致。
  打在自己身上的傷害數字，跟著怪物動作的命中點出現。
```

| 事件 | 什麼時候播放 |
|---|---|
| 其他實體的動作（攻擊、技能、表情、死亡） | 畫面時間（現在 − 100 ms）走到事件時間時 |
| 自己角色的動作（攻擊、技能） | 收到就播放。跟 RO 一樣，客戶端不預測攻擊；事件裡各時間點的間隔（例如揮擊到命中）照樣保留 |
| 發生在自己身上的結果（被打、狀態效果） | 跟著攻擊者動作的命中點出現 |
| 顯示用的數值（HP／SP 條） | 對應的畫面出現時才更新，不會比畫面早 |

單機時網路延遲幾乎是 0，其他實體的動作也一樣晚 100 ms 播放，保持跟多人時相同的程式路徑。

## 9. 興趣範圍

- 用地圖實例的空間格網（01 第 7.2 節），每個 tick 更新每位玩家看得到哪些實體。
- 距離在 50 m 內就進入視野；超過 55 m 才離開，在邊界來回走也不會一直閃爍。
- 進入視野：送 EntityAppear（完整資料）。出現原因照 RO 分兩種：
  - 「已在原地」：實體本來就在，只是你走近了。
  - 「新出現」：生成、重生、傳送抵達。客戶端可以播出現特效。
- 離開視野：送 EntityVanish。消失原因照 RO 分成：
  - 離開視野
  - 死亡
  - 登出
  - 傳送
  - 裝死（RO 初心者的技能，06 決定要不要做）
- 事件只送給看得到相關實體的客戶端。客戶端遇到不認識的實體，就略過那一部分。
- 半徑可以每張地圖分別設定。

## 10. 點怪自動追擊與普攻

```text
客戶端                                         伺服器
點怪（目標在射程外）
自動尋路，轉成一般的移動輸入 ────────────────► 看起來就是普通的移動
走進射程，停下來
AttackStart（目標, 連續）───────────────────► 記住攻擊意圖
                                               條件成立：靜止、在射程內、攻擊時間到
              ◄─────────────────── AttackResult 判定結果，命中時間扣血
播放普攻或暴擊動作，命中點顯示數字
                                               （目標跑出射程）
              ◄─────────────── AttackOutOfRange 不揮擊，等客戶端追上
自動追擊，追上後停下 ─────────────────────────► 條件成立就繼續揮擊
按移動鍵 ─────────── AttackStop ─────────────► 清除攻擊意圖
```

1. **追擊**：目標在射程外時，客戶端用導航網格自動尋路，把路徑轉成一般的移動輸入。伺服器看到的就跟玩家自己走路一樣。
2. **送出意圖**：走到「射程 − 0.2 m」以內就停下、面向目標，送出 AttackStart。已經在射程內就直接送。
3. **伺服器檢查**：目標存在、看得到、還活著、可以攻擊、不在安全區。不符合就回 AttackEnded（附原因）。
4. **揮擊條件**：攻擊時間到了、目標在射程內、角色這個 tick 沒有移動。三個條件都成立才揮擊，並送出 AttackResult。第一下的時間是「現在」和「上一次揮擊＋攻擊間隔」兩者中較晚的那個。
5. **射程**：距離的計算方式在 06 定義。目標正在移動時射程多 1 格（RO 的規則）。
6. **目標跑遠**：揮擊時間到了但目標在射程外，就不揮擊，送出 AttackOutOfRange，客戶端繼續追。同一段追擊只通知一次。
7. **意圖結束**：
   - 客戶端送 AttackStop：玩家按了移動鍵、按 Esc，或改做別的動作。
   - 伺服器送 AttackEnded：單次攻擊打完、目標死亡或消失、角色死亡、換圖、坐下。客戶端收到後停止追擊。
8. **放棄追擊**：目標離開視野或找不到路時，客戶端送 AttackStop。
9. **單次或連續**：協定保留 RO 的兩種模式。預設是連續（00-S02），操作方式在 09。

在 RO 裡，攻擊時角色是站著的，移動就會取消攻擊，目標太遠時會自動走過去。上面的流程在遊戲裡看起來跟 RO 一樣，只有訊息的流程不同（見第 18 節）。

## 11. 換圖

```text
客戶端                                           伺服器
走進傳送點（一般的移動輸入）───────────────────► 偵測到碰到傳送點
                                                 角色移出舊地圖（其他人看到「傳送」消失）
淡出，在背景載入 ◄──────────────── MapChange ── 地圖 ID、位置、面向、移動紀元
                                                 （需要的話，在背景載入新地圖的 logic 場景）
載入完成 ──────────── MapLoaded ──────────────► 角色放進新地圖，開始 3 秒保護
              ◄──────────────── EntityAppear × N 視野內的實體
淡入 ◄─────────────────────────── MapReady
```

1. 伺服器在 tick 裡偵測角色碰到傳送點（簡單的幾何檢查，01 第 7.2 節）。
2. 角色立刻從舊地圖移除，其他人看到原因為「傳送」的消失。這時角色不在任何地圖上：看不到、打不到、也不能行動。移動紀元加 1，舊的輸入全部作廢。
3. 伺服器送出 MapChange。如果新地圖在伺服器上還沒載入，就同時在背景載入它的 logic 場景（01 第 7.2 節）。
4. 客戶端淡出，在背景載入完整的地圖場景，完成後送出 MapLoaded。
5. 伺服器等兩邊都準備好，把角色放進新地圖，送出視野內的實體，最後送 MapReady。客戶端收到 MapReady 才淡入，所以不會看到東西一個一個冒出來。
6. **抵達後的保護（照 RO）**：3 秒內怪物不會注意到你，你也不會受到傷害。只要移動、攻擊或使用技能，保護就提早結束。
7. 載入超過 60 秒沒有回報就斷線，角色存在新地圖的位置。
8. 換圖時存檔一次（第 12.2 節）。

登入進場（第 5.2 節）和死亡後回到儲存點，也走同一套流程。

## 12. 帳號、存檔與安全

### 12.1 帳號

**單機：** 一個固定的本機帳號，不用密碼。伺服器只接受從記憶體傳輸來的本機帳號登入。

**多人（M9）：**
- 帳號由管理指令建立（第 13.4 節），遊戲裡不能註冊。rAthena 的預設也是不開放註冊。
- 長度照 RO：帳號 4～23 個字元（限英數字），密碼 4～32 個字元。
- 密碼雜湊：
  - 演算法是 PBKDF2-HMAC-SHA256，迭代 600,000 次（OWASP 目前的建議）。每個帳號用 16 位元組的隨機鹽。
  - 迭代次數跟雜湊值存在一起，之後要調整時不影響舊帳號。
  - 比對時用固定時間的比較函式，避免從回應時間推測出密碼。
  - Godot 沒有內建 PBKDF2，用它提供的 HMAC 自己組合，並用 RFC 7914 的測試向量驗證結果正確。
  - 雜湊在背景執行緒計算，不會卡住伺服器的 tick。
- 登入失敗：同一個 IP 在 5 分鐘內失敗 7 次，就封鎖 5 分鐘（rAthena 的預設值）。
- 單機和伺服器的角色檔格式相同，可以直接把單機的角色檔複製到伺服器使用，再用管理指令設定它屬於哪個帳號。

### 12.2 存檔

- 只有伺服器寫存檔，客戶端從不寫角色資料。
- 一個帳號一個檔、一個角色一個檔，格式是 JSON（欄位、版本號和遷移規則在 03）。
- 寫入方式：
  - 在主執行緒把資料轉成 JSON 字串，寫檔交給背景執行緒。
  - 先寫到暫存檔再改名取代原檔，寫到一半當機也不會弄壞存檔。
  - 保留上一版當備份。
- 存檔時機：

| 時機 | 依據 |
|---|---|
| 每 300 秒自動存檔，每位玩家的時間錯開 | RO（rAthena 的 autosave_time 是 300 秒，依人數分散） |
| 登出、斷線後角色離開世界時 | RO |
| 伺服器關機 | RO |
| 換圖 | 本專案多加的（列在待檢視） |
| 交易、商店、倉庫等事件之後 | RO；之後有這些系統時再加 |

- 存檔位置：單機在使用者資料夾的 `saves/`，專用伺服器在 `/data/saves/`。
- 第一版只存位置和外觀（01 第 16 節）。

### 12.3 連線安全

- 移動、攻擊、技能、撿東西全部由伺服器檢查（第 4.4 節）。
- **DTLS 加密**（ENet 內建）：
  - 伺服器第一次啟動時，自己產生金鑰和自簽憑證，存在 `/data/cert/`。
  - 把憑證檔複製一份給客戶端，客戶端用它驗證伺服器，防止被冒充或竊聽。
- 伺服器只開一個 UDP 埠。
- 除錯指令只在開發模式接受，專用伺服器預設關閉。

## 13. 部署（M9）

### 13.1 匯出

- 新增一組「Linux 伺服器」匯出設定，資源匯出模式選「Export as dedicated server」。這會自動加上 `dedicated_server` 功能標籤，執行時強制 headless。
- 以下內容整個不打包：`assets/`、各地圖的 `map.tscn` 和地形資料（只留 logic 場景和導航網格）、只有客戶端用的外掛（Terrain3D）、GUT、`tools/`、`tests/`。其他資源用「Strip Visuals」（貼圖和材質換成只保留尺寸的佔位資源）。
  - 伺服器本來就不載入這些東西（01 第 4.3 節的守門測試保證），少打包只是讓檔案變小。
  - 如果有地方誤引用，匯出後的冒煙測試會抓到。
- 開啟「print 時立即寫出標準輸出」（01 第 15 節）。
- 需要 Godot 4.7.2 的 Linux 匯出範本，M9 時安裝。

### 13.2 Docker

- 映像：Debian slim（M9 時選當時的穩定版），加上伺服器執行檔和 pck。不含編輯器和美術素材。
- 用非 root 的使用者執行，只開放 UDP 6900。
- `/data` 掛 volume，放存檔、帳號、憑證、管理指令和狀態檔。log 走標準輸出，用 `docker logs` 就看得到。
- 健康檢查：伺服器每 10 秒更新一次 `/data/status.json`（線上人數、平均 tick 時間），超過 30 秒沒更新就判定不健康。
- 在哪裡跑（你的電腦用 Docker Desktop，或另一台 Linux 機器），以及要不要讓外面的人連進來（開埠或 VPN），M9 時再跟你確認。

### 13.3 設定項目

優先順序：環境變數 → 伺服器設定檔（格式在 03）→ 預設值。

| 環境變數 | 預設 | 說明 |
|---|---|---|
| SERVER_PORT | 6900 | UDP 埠 |
| SERVER_MAX_PLAYERS | 20 | 同時在線人數上限 |
| SERVER_DATA_DIR | /data | 存檔、帳號、憑證、管理指令、狀態檔的位置 |
| SERVER_TICK_RATE | 30 | 模擬頻率（Hz） |
| SERVER_SNAPSHOT_RATE | 30 | 快照頻率（30 或 15） |
| SERVER_DTLS | on | 是否加密 |
| SERVER_AUTOSAVE_SEC | 300 | 自動存檔間隔（秒） |
| SERVER_LOG_LEVEL | INFO | log 等級 |
| SERVER_DEBUG_COMMANDS | off | 是否接受除錯指令 |

### 13.4 管理指令與關機

- 伺服器每秒檢查一次 `/data/admin/` 裡有沒有指令檔（JSON）。處理完就刪除，結果寫進 log。
- 指令包括：建立帳號、改密碼、指定角色所屬帳號、踢人、關機。之後可以再加公告、封鎖。
- M9 會提供 PowerShell 腳本，透過 `docker exec` 放入指令檔。含密碼的指令檔在伺服器處理完（約 1 秒內）就會刪除。
- 關機流程：停止接受新連線 → 所有人存檔 → 通知客戶端「伺服器關閉中」→ 結束程式。
- 為什麼要繞這一圈：
  - Godot 在 Linux 收到 SIGTERM（`docker stop` 送的訊號）會直接結束，不會跑存檔流程。這是 Godot 的已知問題（godot-proposals #1361），目前還沒有解決。
  - 所以容器的入口腳本會攔下 SIGTERM，改成放一個「關機」指令檔，再等伺服器自己結束，最多等 25 秒。
  - Docker 的停止等待時間設成 30 秒。
  - M9 時會再確認一次 Godot 4.7 的行為；如果那時已經支援 SIGTERM，就把這一層拿掉。

## 14. 網路模擬與除錯數據

| 名稱 | 往返時間 | 抖動 | 掉包 | 亂序 |
|---|---|---|---|---|
| local（本機） | 0 | 0 | 0% | 無 |
| good（良好） | 60 ms | ±5 ms | 0% | 無 |
| normal（普通） | 120 ms | ±15 ms | 1% | 無 |
| bad（惡劣） | 250 ms | ±40 ms | 5% | 有 |

- 掉包和亂序只發生在即時頻道。可靠頻道的「掉包」用多等一個往返時間來模擬重送，後面的封包也會一起被卡住，跟真實的 ENet 一樣。
- 整合測試用 good 和 bad 兩組條件跑。
- 單機模式可以用啟動參數（例如 `--netsim=bad`）開啟，讓你提早體驗多人連線的手感。
- 除錯數據（由 10 的 F3 面板顯示）：
  - 往返時間、掉包率
  - 每秒收送的位元組數
  - 快照緩衝的深度（ms）
  - 預測校正的次數和最大誤差
  - 時鐘的偏差
  - 視野內的實體數

## 16. 測試與驗收方式

**M0（協定骨架）：**
1. 每種訊息編碼後再解碼，內容完全相同，包含各型別的邊界值。
2. 用固定種子產生隨機位元組、截斷的封包、超長的封包丟給解碼器：不能當掉，而且要正確拒絕。
3. 協定指紋測試：改了訊息目錄卻沒改版本號，測試就失敗。
4. 握手：版本不同、資料雜湊不同時，會被拒絕並帶正確的原因。
5. 時間同步：在 good 條件下，估算誤差 ≤ 5 ms；在 bad 條件下 ≤ 20 ms。
6. 單機模式用 headless 跑 60 秒：進入地圖、持續收到快照，沒有任何錯誤（同 01 第 17 節）。

**M1（移動和換圖，1 個伺服器加 2 個客戶端，記憶體傳輸）：**
1. 客戶端 A 照腳本走一段路。結束後，A 的預測位置跟伺服器位置相差 ≤ 1 cm；B 看到的 A 在 0.2 秒內收斂到同一個位置。
2. 在 bad 條件下重複第 1 項：沒有錯誤，最後的位置一致。校正次數記錄下來，當作之後調整的基準。
3. 加速作弊：讓客戶端每秒送 60 個輸入，伺服器上的移動速度不會超過正常速度。
4. 快照差量：在 10% 掉包下跑 60 秒，B 重建出的每個實體狀態都跟伺服器一致。
5. 興趣範圍：A、B 的距離從 60 m 走到 40 m 再走回 60 m，在 50 m 時出現、55 m 時消失；在邊界來回走不會閃爍。
6. 換圖：
   - A 走進傳送點，B 看到 A 以「傳送」原因消失。
   - 載入期間 A 送出的移動輸入被忽略。
   - A 回報載入完成後出現在新地圖。
   - 3 秒保護在 A 移動時解除。
7. 指令順序：A 停下的同時送出坐下，伺服器上 A 停的位置跟客戶端一致，沒有被拉回。

**M5（戰鬥）：**
1. 點遠處的怪：自動追擊 → 進入射程 → 照攻擊間隔連續揮擊。
2. 目標跑開時收到 AttackOutOfRange，追上後繼續打；按移動鍵就停止。
3. 角色移動中不會揮擊。

**M9（多人）：**
1. 本機 ENet 迴路：一個 headless 伺服器程序加兩個客戶端程序，跑 M1 的同一組情境，結果一致。
2. 開啟 DTLS 可以連線；憑證不符時拒絕連線。
3. 帳號：建立、登入、密碼錯誤、連續失敗 7 次後封鎖 5 分鐘、重複登入。PBKDF2 用 RFC 7914 的測試向量驗證。
4. 斷線：戰鬥後 10 秒內斷線，角色在世界上多留 10 秒；不在 10 秒內就立即移除。兩種情況都有存檔。
5. Docker：映像可以建置；容器啟動後能連線；`docker stop` 之後存檔完整，log 裡有正常關機的紀錄。
6. 效能：模擬 20 個客戶端時，伺服器每個 tick ≤ 10 ms（01 第 14 節），並記錄每位玩家的頻寬。

## 17. 風險與備案

| 風險 | 影響 | 備案 |
|---|---|---|
| GDScript 編碼快照的成本 | 20 人加上很多怪物時，tick 變慢 | M1 就用模擬的 20 個客戶端量測；不夠時把快照降到 15 Hz，或讓怪物改送 RO 式的「移動路徑」事件，由你決定 |
| 客戶端和伺服器的計算結果有微小差異（Windows 和 Linux 的浮點運算） | 一直出現小幅校正 | 校正門檻 1 cm 加上平滑；M9 用 Windows 客戶端連 Linux 伺服器實測 |
| Godot 收到 SIGTERM 不會正常關閉 | `docker stop` 時可能遺失資料 | 入口腳本轉成關機指令（第 13.4 節）；平常也有自動存檔 |
| DTLS 在實際環境中有問題 | 不能加密連線 | 改用 VPN（例如 WireGuard）保護連線，伺服器關閉 DTLS |
| 在 GDScript 裡跑 PBKDF2 太慢 | 登入要等很久 | 已經放在背景執行緒；M9 實測單次登入超過 2 秒時，再提出調整方案讓你決定 |
| 朋友在 NAT 或防火牆後面 | 連不進來 | M9 時再決定要開埠還是用 VPN |
| 可靠頻道掉包時後面的封包被卡住 | 事件晚到約一個往返時間 | 聊天已經分開；快照和輸入走不可靠頻道，不受影響 |
| 換圖時載入太久 | 等待時間變長 | 畫面在淡出狀態，玩家看不到；60 秒逾時；載入時間列入 01 的效能預算（≤ 5 秒） |

## 18. 與 RO 原制不同之處（待檢視）

| 項目 | RO 原制 | 本專案 | 理由 |
|---|---|---|---|
| 連線方式 | TCP；登入、角色、地圖三種伺服器分開 | ENet（UDP）；一個伺服器程序 | 連續移動需要不可靠的高頻更新；20 人的規模不需要拆伺服器。玩家感受不到差別 |
| 移動同步 | 點地面後送出目標格，伺服器算出路徑後廣播，其他人照路徑播放 | 每 33 ms 送一次方向輸入，自己的角色先預測；其他人用快照插值 | 00-S02 選了 WASD（01 第 19 節已列出移動方式的差異），這裡是對應的同步方式 |
| 可視範圍 | 14 格 | 50 m 內出現，超過 55 m 才消失 | 3D 自由鏡頭看得遠，14 m 會看到怪物在身邊突然冒出來。M1 截圖後再調整 |
| 其他實體的動作時間 | 收到就播放 | 晚 100 ms 播放，跟插值後的位置對齊 | 讓動作和位置一致。RO 本來也有網路延遲，玩家很難分辨 |
| 點怪攻擊的訊息流程 | 點怪就送出攻擊要求；距離太遠時伺服器通知客戶端，客戶端走過去後再送一次 | 客戶端先自動走進射程，再送攻擊意圖；伺服器記住意圖，目標跑遠時通知客戶端再追 | 01 第 3.2 節的流程。遊戲裡看到的行為一樣：站著打、移動就取消、太遠會自動走過去 |
| 點怪的預設行為 | 點一下只打一下；按住 Ctrl 或開啟 /noctrl 才連續攻擊 | 預設連續攻擊；協定保留單次和連續兩種 | 00-S02 已經決定，這裡只是記錄 |
| 存檔時機 | 每 300 秒（錯開）、登出、交易等特定事件之後 | 同 RO，另外在換圖時也存 | 減少當機時遺失的進度，不影響遊戲 |
| 帳號安全 | rAthena 預設把密碼明文存放；官方用自己的封包加密 | 密碼用 PBKDF2 雜湊；多人連線用 DTLS 加密 | 安全性，不影響遊戲 |

除了上表，本文件的其他規則都照 RO：
- 登出和斷線的 10 秒規則
- 重複登入的處理
- 換圖的流程和抵達後的 3 秒保護
- 出現和消失的原因分類
- 攻擊時站著不動、移動就取消攻擊
- 目標移動中射程多 1 格
- 登入失敗的封鎖次數和時間
- 登入時回到上次登出的位置

**Godot 4.7 文件**
- ENetConnection（建立主機、service、壓縮、DTLS）：https://docs.godotengine.org/en/4.7/classes/class_enetconnection.html
- ENetPacketPeer（傳送旗標、連線統計、逾時、ping 間隔）：https://docs.godotengine.org/en/4.7/classes/class_enetpacketpeer.html
- SceneMultiplayer（驗證回呼、server_relay 預設開啟、send_bytes）：https://docs.godotengine.org/en/4.7/classes/class_scenemultiplayer.html
- 專用伺服器匯出（Export as dedicated server、Strip Visuals、dedicated_server 功能標籤強制 headless）：https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_dedicated_servers.html
- Crypto（HMAC、固定時間比較、自簽憑證；沒有內建 PBKDF2）：https://docs.godotengine.org/en/4.7/classes/class_crypto.html
- ENet 預設值（MTU 1,392、逾時 5～30 秒、ping 間隔 500 ms），Godot 4.7.2 內附的 enet.h：https://github.com/godotengine/godot/blob/4.7-stable/thirdparty/enet/enet/enet.h
- Godot 在 Linux 收到 SIGTERM 無法執行關閉流程（尚未解決的提案）：https://github.com/godotengine/godot-proposals/issues/1361

**RO 機制（只參考行為，不抄程式碼）**

rAthena 是模擬官方行為的伺服器模擬器，以下引用它的設定預設值和原始碼註解：
- 可視範圍 14 格（area_size）：https://github.com/rathena/rathena/blob/master/conf/battle/client.conf
- 抵達地圖後 3 秒保護（player_invincible_time）、登出限制 10 秒與觸發條件（prevent_logout、prevent_logout_trigger）：https://github.com/rathena/rathena/blob/master/conf/battle/player.conf
- 攻擊動作中客戶端不送移動、被打時停在最近的格子中心、延遲傷害（delay_battle_damage）：https://github.com/rathena/rathena/blob/master/conf/battle/battle.conf
- 自動存檔 300 秒並依人數分散、特定事件後存檔：https://github.com/rathena/rathena/blob/master/conf/map_athena.conf
- 登入失敗封鎖（5 分鐘內 7 次、封鎖 5 分鐘）、預設不開放註冊、預設密碼明文：https://github.com/rathena/rathena/blob/master/conf/login_athena.conf
- 單次和連續攻擊、移動和攻擊會取消保護、斷線時角色多留 10 秒、戰鬥中不能登出、消失原因分類、「距離太遠」通知：https://github.com/rathena/rathena/blob/master/src/map/clif.cpp
- 目標移動中射程多 1 格、移動會取消攻擊：https://github.com/rathena/rathena/blob/master/src/map/unit.cpp
- 重複登入時拒絕新登入並踢掉舊連線：https://github.com/rathena/rathena/blob/master/src/login/loginclif.cpp
- 帳號和密碼長度：https://github.com/rathena/rathena/blob/master/src/common/mmo.hpp 、https://github.com/rathena/rathena/blob/master/src/login/login.cpp
- /noctrl：只點一次就能連續攻擊（iRO Wiki）：https://irowiki.org/wiki/Battle_mode

**安全**
- OWASP 密碼儲存建議（PBKDF2-HMAC-SHA256 600,000 次）：https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html
- RFC 7914 第 11 節（PBKDF2-HMAC-SHA256 測試向量）：https://www.rfc-editor.org/rfc/rfc7914#section-11
