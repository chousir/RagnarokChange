## 2. 項目 2：顯示文字與多語言

### 2.1 現況

- 03-D02：資料全用英文，**名稱和說明也在資料裡**（例如 `data/jobs/jobs.json` 的 `"name": "Swordsman"`）。
- 03-D17、第 7 節：英文基準是「資料的名稱和說明」加上 `locale/en/`；繁中放在 `locale/zh_TW/`。只有客戶端讀，不算進資料雜湊。
- 程式（`src/client/locale/locale_catalog.gd`）：把英文和繁中各建成一份 Godot 的翻譯，語系**固定**設成 `zh_TW`，缺字退回英文。
- 00-S13、03-D14：地圖的中文顯示名稱是「KRONENBERG王都」「王都南方草原」。

### 2.2 問題

1. 「KRONENBERG王都」中英混合。
2. 英文顯示文字一半在 `data/`、一半在 `locale/en/`：
   - 改一個英文名稱就會改到資料雜湊（02 第 4.3 節），多人時伺服器也要跟著更新，但伺服器根本用不到顯示文字。
   - 英文和中文的地位不對等，之後加第三種語言時，誰是「基準」會不清楚。
3. 語系寫死在程式裡，沒辦法切換；加語言要改程式。

### 2.3 建議的做法

**（1）顯示文字全部移出 `data/`**

- 資料只留 `id`、`ro_ref`、`note`（給開發看的英文備註），不放任何玩家看得到的文字。
- 每個資料項目的名稱和說明，各語言都放在 `locale/<語系>/`，鍵照現在的格式（`job.swordsman.name`、`item.knife.desc`）。
- 好處：改任何語言的文字都不會動到資料雜湊和伺服器；每種語言地位相同。

**（2）每種語言一個資料夾，加一份語言清單**

```text
locale/
  locales.json            語言清單
  zh_TW/                  繁體中文（預設）
    names.json  ui.json  messages.json  enums.json
  en/                     英文
    names.json  ui.json  messages.json  enums.json
  （之後）ja/、ko/、zh_CN/…：放一樣的檔案，可以不完整
```

`locales.json` 的內容（示意）：

```text
{
  "table": "locales",
  "entries": [
    { "id": "zh_TW", "native_name": "繁體中文", "fallback": "en", "required": true,  "font": "noto_sans_tc" },
    { "id": "en",    "native_name": "English",  "fallback": "",   "required": true,  "font": "noto_sans_tc" }
  ]
}
```

- `required: true` 的語言每個鍵都要有，缺了測試就失敗；之後加的語言可以設 `false`，缺的鍵依 `fallback` 退回（例如日文缺字顯示英文），測試只列出完成度。
- 加一種語言 ＝ 加一個資料夾和清單裡的一行，不用改程式。

**（3）執行中切換**

| 項目 | 做法 |
|---|---|
| 啟動 | 讀 `settings.cfg` 的 `[ui] language`（03 第 9.2 節已經有「顯示語言，預設 zh_TW」），只載入這個語言和它的退回語言，省記憶體 |
| 切換 | 載入新語言 → `TranslationServer.set_locale()` → 卸載用不到的語言。介面節點開了自動翻譯（`auto_translate_mode`）會自己更新；程式組出來的文字在收到 `NOTIFICATION_TRANSLATION_CHANGED` 時重組 |
| 複數 | 英文有單複數（1 item、2 items），中文沒有。文字項目可以多一個 `plural` 欄位，用 Godot 4.7 `Translation` 的 `add_plural_message` 登記，程式用 `tr_n` 取 |
| 伺服器送的訊息 | 伺服器只送訊息 ID 和參數（02 已定）。參數如果是資料 ID（例如物品），客戶端依目前的語言轉成名稱；訊息欄存的是「ID＋參數」，所以切換語言後，舊訊息也會用新語言重新顯示 |
| 字型 | 繁中和英文都用 Noto Sans TC（裡面有英文字母）。之後加日文、韓文、簡中時，清單裡指定 Noto Sans JP／KR／SC，切換時才載入 |
| 截圖 | 自動截圖加一個參數 `--lang=en`，同一組觀測點可以各截一次中英文 |

**（4）術語表**

- 新增 `docs/glossary.md`：每個專有名詞和遊戲術語的中英對照、翻譯規則。翻譯和改文字時都照這張表，前後才會一致。
- 規則（建議）：
  - 職業、技能、素質優先用台灣版 RO 的官方譯名（06 第 8.2 節已經這樣規劃）。
  - 地名、人名、組織名：音譯或意譯擇一，整份表一致；不中英混合。
  - 中文用全形標點，數字用半形。

**（5）防止中英混用的測試**

| 測試 | 內容 |
|---|---|
| 完整 | 每個資料項目（職業、地圖、怪物、物品…）在 `required` 的語言都有名稱；每個介面、訊息的鍵在 `required` 的語言都有文字 |
| 參數 | 同一個鍵在各語言的參數（`{item}`）完全一樣（現在已經有） |
| 不混用 | 繁中文字裡不能有英文字母，只允許白名單（例如 `HP`、`SP`，看第 9 節第 4 項）和參數；英文文字裡不能有中文字元 |
| 寫死的文字 | 用 Godot 內建的「偽本地化」（pseudolocalization，把所有翻譯過的文字加上記號和長度）跑一次自動截圖：沒有被轉換的文字就是寫死在程式或場景裡的；也順便看英文變長時版面會不會爆掉 |

## 3. 項目 3：靜態資料和動態狀態解耦、3D 標準單位

### 3.1 現況

已經分開的部分：
- `data/` 載入後唯讀（01 第 10 節、03-D07）；存檔只存 ID 字串（03 第 8 節）。
- 地圖分成 logic 場景（標記、導航網格）和完整場景（03-D15、08-D05）。
- 規則和表現分開：`visual_id` 對應客戶端的 `.tres`（03-D13）。
- 規則常數、伺服器設定、客戶端設定分在三個地方（03-D12、03-D22）。

還沒講清楚的部分：
- 「定義」「執行中的狀態」「算出來的值」三者的規則沒有寫成文字，例如物品的定義和「這一把劍」（精煉值、卡片、隨機屬性）怎麼分。
- 怪物生成區（03 第 6.2 節）把**位置**（場景）和**內容**（哪種怪、幾隻、重生時間）放在同一個標記上，調整數量要改場景。
- 距離和速度照 RO 存格數（03-D05），載入時才換成公尺；但 3D 需要的東西（身體大小、高度差、扇形範圍）用格子表達不了。

### 3.2 建議：定義、狀態、衍生值三層

| 層 | 內容（例子） | 誰寫 | 生命週期 | 放在哪裡 |
|---|---|---|---|---|
| 定義（唯讀） | 職業、技能、物品、怪物、規則常數、生成表、隨機屬性群組 | 開發者（JSON） | 啟動時載入，執行中不變 | `data/`（算進資料雜湊） |
| 狀態（動態） | 角色、這一把劍（精煉、卡片、隨機屬性）、場上的怪物、狀態效果、冷卻、地上的掉落物 | 伺服器 | 執行中會變；需要保留的才存檔 | 伺服器記憶體的元件、存檔 |
| 衍生值（快取） | 素質加總、ATK、ASPD、移動速度 | 伺服器依「定義＋狀態」算出 | 依賴的東西變了才重算（髒旗標） | 記憶體；不存檔、不相信客戶端 |

規則：
1. 狀態只用 ID（存檔、網路）或 u16 索引（執行中、網路）指向定義，**不複製定義的數值**。所以改了平衡數值，舊角色和舊物品馬上套用新值。
2. 定義載入後凍結：Godot 的 `Dictionary` 和 `Array` 有 `make_read_only()`，不小心寫入時會直接報錯。
3. 衍生值不存檔。存檔只放狀態（03 第 8 節本來就是這樣，寫成規則）。
4. 物品實例的欄位（03 第 8.3 節的 inventory）定成：`uid`（每件裝備唯一）、`item`（定義的 ID）、`amount`、`refine`、`cards`、`random_options`（第 4 節）、`identified`、`broken`、`bound`。可以堆疊的物品（消耗品、材料）沒有 `uid`。
5. 怪物生成：logic 場景的標記只放**範圍和一個 `spawn_id`**；內容（怪物、數量、重生時間）放在 `data/spawns/<地圖 ID>.json`。調數量不用開場景，也算進資料雜湊。

效能上的好處：定義用陣列和 u16 索引查；衍生值有快取，不會每個 tick 重算 ASPD；網路和存檔都只送狀態。

### 3.3 建議：資料一律用 3D 標準單位

**單位表（取代 03 第 3.3 節）：**

| 種類 | 單位 | 欄位後綴 | 例子 |
|---|---|---|---|
| 時間 | 毫秒（整數） | `_ms` | `attack_interval_ms` |
| 距離、範圍、射程、尺寸、位置 | 公尺（最多 2 位小數） | `_m` | `attack_range_m`、`body_radius_m` |
| 速度 | 公尺／秒（最多 2 位小數） | `_mps` | `move_speed_mps` |
| 角度 | 度 | `_deg` | `cone_angle_deg` |
| 重量、機率、比例 | 不變（03-D06） | — | — |

- 拿掉 `_cells`、`_ms_per_cell` 和 `data/rules/` 的 `cell_size_m`。執行中本來就只用公尺（03 第 3.3 節），所以程式只是少一步換算。
- RO 的原始值怎麼追：`ro_ref` 照樣記來源；換算規則寫在 06 第 3 節的「RO 換算表」（下表）。填資料時照表換算，數值檢查時照表換回去對照。

**RO 換算表（建議放進 06 第 3 節）：**

| RO | 換算 | 例子 |
|---|---|---|
| 距離 N 格 | N 公尺（基準：1 格 ＝ 1 公尺，跟現在一樣） | 攻擊距離 1 格 → `attack_range_m: 1` |
| 移動速度 N 毫秒／格 | 1000 ÷ N 公尺／秒 | 150 → 6.67；400 → 2.5 |
| 方形範圍（半徑 k 格，也就是 (2k＋1) × (2k＋1) 格） | 圓形，半徑 k＋0.5 公尺 | 怒爆的範圍 2 → 半徑 2.5 m |
| 擊退 N 格 | 沿著攻擊方向推 N 公尺，貼著導航網格滑動 | — |
| 目標移動中射程多 1 格 | 多 1 公尺 | `moving_target_range_bonus_m: 1` |

**3D 才需要的東西（新增）：**

| 項目 | 內容 | 理由 |
|---|---|---|
| 身體半徑 `body_radius_m`、身高 `height_m` | 每種怪物、NPC 各有；玩家用規則常數（半徑 0.4 m，跟導航網格一樣） | 3D 的怪物大小差很多 |
| 距離改成「邊緣到邊緣」 | 射程判定用「水平中心距離 − 攻擊者半徑 − 目標半徑」，取代 06-D03 的「＋0.5 格」 | 大型怪物（半徑 1.5 m）用中心距離算的話，近戰 1 m 根本打不到；FF14 的怪物也有大小不同的目標圈，距離從圈的邊緣算（見第 10 節的來源） |
| 高度差上限 | 攻擊和技能的雙方高度差不能超過 3 m（規則常數） | 06-D03 忽略高度，站在橋上或懸崖上會打到下面的怪 |
| 範圍的形狀 | 技能範圍寫成形狀：圓、方、扇形、直線，例如 `{"shape": "cone", "radius_m": 5, "angle_deg": 90}` | 3D 技能的範圍表現；RO 的方形範圍照上表換成圓 |
| 視線檢查（之後） | 遠程攻擊和技能要看得到目標（RO 有，牆會擋） | M5 之後再做；伺服器沒有物理引擎，要另外從 logic 場景烘焙簡單的遮擋資料 |

- RO 的體型（small、medium、large）仍然保留，那是戰鬥規則（體型修正），跟實際的身體大小分開。

## 4. 項目 4：裝備的隨機附魔

> 2026-10-10 更新：你給了兩張附加能力池的表（最多 3 條、第 3 條機率取得），**本節已由 `2026-10-10-review-round-2.md` 第 4 節取代**。下面保留當作背景（RO 官方的隨機選項制度）；「最多 5 條」「必出格＋額外格」的部分以第二輪為準。

### 4.1 RO 本身的制度（隨機選項）

我查了 rAthena master（只參考行為，不抄程式碼）：

- 每件裝備最多 **5 條**隨機選項。
- 「群組」決定會出哪些選項：
  - 必出的格子：每一格有一份候選清單，從裡面挑一條（各候選有機率；都沒挑中時隨便給一條）。
  - 額外的格子：最多幾格，每格從另一份候選清單挑一條，依機率決定有沒有出。
  - 每條的數值在「最小～最大」之間隨機。
- 怪物的掉落表裡，每一筆掉落可以指定一個群組，掉出來時就擲好選項。rAthena 的 Renewal 怪物資料裡有 179 筆掉落指定了群組；果凍怪參考的 Poring 掉的短劍（Knife_）也有一行群組設定，只是被註解掉了。
- 每條選項本身就是一個裝備效果（例如力量 ＋N、最大 HP ＋N）。

所以「打怪掉的武器防具有隨機附魔」**照 RO 做就有**，不算加入 RO 沒有的機制。

「RO 樂園」：我搜尋後沒辦法確定是哪一個版本或伺服器，也查不到它的隨機屬性規則。請你描述喜歡的地方（例如條數、名稱顏色、可以重洗、有沒有特殊效果），我再對照調整（第 9 節第 17 項）。

### 4.2 建議的資料

**選項定義**（`data/random_options/`）：每條選項是一個效果（第 5.2 節）加上固定參數。

```text
{

  "entries": [
    { "id": "str_add",          "effect": "stat_add",        "stat": "str",    "ro_ref": "VAR_STRAMOUNT" },
    { "id": "max_hp_add",       "effect": "max_hp_add",                         "ro_ref": "VAR_MAXHPAMOUNT" },
    { "id": "atk_add",          "effect": "atk_add",                            "ro_ref": "VAR_ATKAMOUNT" },
    { "id": "damage_vs_plant_pct", "effect": "damage_vs_race_pct", "race": "plant" }
  ]
}
```

**群組**（`data/random_option_groups/`）：

```text
{
  "table": "random_option_groups",
  "entries": [
    {
      "id": "field_weapon_t1",
      "guaranteed": [
        { "options": [
          { "option": "atk_add", "min": 1, "max": 10, "chance_pct": 50 },

        { "option": "dex_add",             "min": 1, "max": 3, "chance_pct": 20 },

}
```

**掉落**（03 第 4.5 節的 `drops`）：每筆掉落可以加 `random_option_group`，照 RO 的寫法。

**物品實例**（第 3.2 節第 4 條）：`random_options: [{option, value}]`，最多 5 條，存進存檔。

### 4.3 規則

| 項目 | 規則 |
|---|---|
| 什麼時候擲 | 掉落的那一刻，在伺服器用地圖實例的亂數產生器（01-D17）；地上的物品已經帶著選項 |

## 5. 項目 5：擴充性和存檔

### 5.1 新增欄位好不好加

現在的做法（03-D07）：每種資料在 shared 有一個定義類別，同時是驗證規則。加一個欄位的步驟：

1. 在定義類別加一行欄位宣告（型別、範圍、預設值、從哪個里程碑開始）。
2. 資料檔填值（有預設值的欄位，舊資料可以不填）。
3. 程式使用它。
4. 驗證和測試自動涵蓋（型別錯、範圍錯、未知欄位都會被抓到）。

建議再加兩個規則，讓「只有某一類才有的欄位」更好加：

- **共通欄位＋分類區塊**：物品的共通欄位放外層，武器、防具、消耗品各自的欄位放在自己的區塊（例如 `"weapon": {...}`），每個區塊各有定義類別。加武器專屬的欄位只改武器區塊。
- **定義和狀態分開加**（第 3.2 節）：只影響定義的欄位（例如武器的新屬性）不用改存檔；屬於狀態的欄位（例如每件裝備的耐久度）要在物品實例加欄位，並寫一步存檔遷移（03 第 8.4 節已經有遷移框架）。

### 5.2 效果好不好加：建議改成「有名字的效果類型」

03 第 4.7 節現在寫 `bonuses: [{type, value}]`，種類由 06 定。建議把它做成一套共用的效果系統：

```text
"bonuses": [
  { "effect": "stat_add",            "stat": "str",  "value": 2 },
  { "effect": "damage_vs_race_pct",  "race": "plant", "value": 10 },
  { "effect": "autocast_on_attack",  "skill": "bash", "level": 3, "chance_pct": 5 },
  { "effect": "atk_add",             "value": 10, "when": { "refine_at_least": 7 } }
]
```

| 規則 | 內容 |
|---|---|
| 效果類型 | 每種效果在 shared 有一個定義（名稱、參數和型別），伺服器有一個處理器。名稱照用途取（`stat_add`、`damage_vs_race_pct`），對照 RO 的 bonus 腳本記在 `ro_ref` |
| 誰用 | 裝備的固定效果、卡片、隨機選項（第 4 節）、狀態效果的數值修正、被動技能，全部用同一套 |
| 條件 | 選填的 `when`（精煉值、職業、武器種類、對象的種族等），一樣有定義和驗證 |
| 加新效果 | 加一個效果定義＋一個處理器＋測試；資料就能用。驗證會擋住未知的效果名稱和錯的參數 |
| 計算 | 所有來源的效果先收集成「修正值清單」，再一次算出衍生值（第 3.2 節），不會每種來源各算一遍 |
| 特殊的 | 太特別、沒辦法用參數表達的效果（RO 少數裝備的腳本），寫成有名字的專用處理器；不發明腳本語言（跟 03 第 4.4 節技能的做法一致） |

### 5.3 JSON 好不好

| 項目 | 評估 |
|---|---|
| 當資料來源 | 好：Godot 內建、好比對差異、伺服器不用載入美術素材、驗證已經寫好 |
| 載入速度 | 第一版的資料量（幾百筆）載入很快。資料到幾千筆、啟動超過 1 秒時，加一個「匯出時把 JSON 轉成二進位快取」的步驟，JSON 還是唯一的來源 |
| 大張的數值表 | 經驗表、HP／SP 表很長。可以維持 JSON；如果你想用試算表編，可以加 CSV 轉 JSON 的工具（不急） |

結論：保留 JSON。

### 5.4 一個角色一個檔好不好

| 項目 | 一角色一檔（現在） | SQLite（建議 M9 前改） |
|---|---|---|
| 單機、開發 | 好：直接打開就看得懂，壞了也好修 | 要用工具才看得到（可以提供匯出 JSON 的工具） |
| 兩個角色同時改（交易、郵件、公會倉庫） | **不安全**：要寫兩個檔，寫到一半當機會讓物品複製或消失 | 一個交易（transaction）裡改完，要嘛全部成功、要嘛全部沒發生 |
| 名稱不重複的檢查 | 要自己建索引，伺服器啟動時掃全部的檔 | 唯一索引，查詢很快 |
| 寫入的安全 | 03 第 8.5 節的三步寫入和備援 | SQLite 本身保證（WAL 模式） |
| 備份 | 複製資料夾 | 不停機的線上備份（`VACUUM INTO`） |
| 依賴 | 沒有 | 要一個 GDExtension（例如 godot-sqlite，支援 Godot 4、Windows、Linux 和專用伺服器）；版本要在用之前查證（00-S09） |
| 多個伺服器程序（第 6 節第 3 階段） | 不行 | 也不夠，要換 PostgreSQL 這類資料庫 |

建議：
- M8 之前（單機、沒有交易）維持一角色一檔，不用改。
- **M9 多人之前**改成 SQLite：程式已經有 `AccountStore` 介面（`src/server/accounts/`），加一個 SQLite 的實作即可。角色資料仍然存成 JSON（放在一個欄位裡，遷移規則照舊），另外把名稱、帳號、地圖拉成欄位方便查詢。交易、倉庫、郵件一律在一個交易裡完成。
- 單機要不要也改用 SQLite：建議也改（單機和多人走同一條程式路徑，跟 01-D03 的精神一致），另外提供「匯出成 JSON」的除錯工具。這點請你決定（第 9 節第 19 項）。

## 6. 項目 6：多人規模、分流、私人房間

### 6.1 現況

- 02-D21：同時在線 20 人；一個伺服器程序承載所有地圖；模擬在單一執行緒。
- 01 第 7.2 節：每張地圖一個「地圖實例」，有自己的導航地圖、空間格網、亂數產生器。

### 6.2 人數上限取決於什麼

| 瓶頸 | 說明 | 粗估 |
|---|---|---|
| 伺服器 CPU | GDScript 跑模擬：移動、AI、戰鬥、興趣範圍、**快照編碼**。快照的成本大約是「玩家數 × 每人視野內在動的實體數」 | 照 02 的做法，單執行緒大約 50～80 人就會碰到 tick 預算（01 第 14 節的 10 ms 是給 20 人的）；要用壓力測試確認 |
| 頻寬 | 02 第 3.4 節：每人下行約 45～310 kbps | 200 人約 9～62 Mbps 上傳，家用光纖勉強，機房的主機沒問題 |
| 玩家的電腦 | 一個完整角色約 6 萬個三角形（04 第 12 節），50 個角色擠在一起就超過 01 第 14 節的畫面預算 | 要有「最多顯示幾個角色」的設定、遠處用低階 LOD（FF14 也有顯示人數的設定） |
| 存檔 | 一角色一檔 | 多人交易前改 SQLite（第 5.4 節） |

### 6.3 建議分三階段

| 階段 | 架構 | 目標人數（要壓力測試確認） | 什麼時候 |
|---|---|---|---|
| A | 現在的架構：一個程序、所有地圖、單執行緒 | 約 50 人 | M9 |
| B | 加上**分流**和**地圖實例分散到多個執行緒**（地圖之間互不影響，可以平行）；快照的優化（第 6.6 節） | 約 150～200 人 | M9 之後 |
| C | 多個伺服器程序，各管一部分地圖；前面一個登入和分配的程序；資料庫改 PostgreSQL；換圖可能跨程序 | 數百人以上 | 真的需要時 |

- M9 加一項壓力測試：用 headless 的機器人客戶端模擬 20、50、100 人，記錄 tick 時間和頻寬，數字寫進報告再決定下一階段。
- 熱點程式（快照編碼、興趣範圍）如果 GDScript 不夠快，可以改寫成 C++ 的 GDExtension；先量測再決定。

### 6.4 分流（同一張地圖開好幾份）

| 項目 | 建議 |
|---|---|
| 識別 | 地圖實例 ＝ 地圖 ID ＋ 實例編號（例如 `kronenberg#2`）。**現在就把程式和協定改成這樣**（MapChange 加上實例編號），之後加分流不用再改協定 |
| 每份的人數上限 | 每張地圖可以設定（`data/maps/` 加 `max_players_per_instance`，建議預設 60～80；城鎮可以高一點） |
| 自動分配 | 進入地圖時：先放到隊友所在的分流 → 否則選人數最少而且沒滿的 → 都滿了就自動開一份新的 |
| 手動切換 | 介面上選分流；在城鎮或非戰鬥中才可以換（套用 02 的 10 秒規則，不能拿來逃離戰鬥）；切換就是同一張地圖的換圖流程（淡出淡入） |
| 怪物 | 每份分流各自生成，互不影響 |
| 存檔 | 只存地圖 ID，不存分流編號；登入時重新分配 |
| 聊天 | 密語和公會跨分流；附近的對話只在同一份 |
| 自動關閉 | 編號 2 以上的分流沒有人時，5 分鐘後關閉 |

### 6.5 私人房間（邀請制）

RO 本身有「副本」（Memorial Dungeon）：隊伍建立一份專屬的地圖，有存在時間和閒置時間的上限（rAthena 的預設是存在 3600 秒、閒置 300 秒）。你說的「自己開房間私自邀請」可以用同一套機制：

| 項目 | 建議 |
|---|---|
| 種類 | （1）隊伍副本：照 RO，之後的地城用；（2）私人房間：任何野外地圖都可以開一份私人的，只有被邀請的人能進（RO 沒有，列在「與 RO 原制不同之處」） |
| 建立 | 在地圖入口或用指令建立；建立的人是房主 |
| 邀請 | 用角色名稱邀請，或產生一組邀請碼；房主可以踢人；人數上限 12（RO 的隊伍上限） |
| 存在時間 | 沒有人之後 5 分鐘關閉（照 RO 的閒置時間）；私人房間不設總時間上限，隊伍副本照 RO |
| 關閉時 | 裡面的人送回來源地圖的入口抵達點 |
| 登出再登入 | 房間還在而且你還在名單上 → 回到房間；否則 → 來源地圖的入口 |
| 經驗和掉落 | 跟公開的一樣，不加成 |
| 上限 | 每台伺服器同時最多幾個私人房間（記憶體），由伺服器設定 |

### 6.6 優化清單

| 地方 | 做法 |
|---|---|
| 快照 | 每個實體每個 tick 只編碼一次，給所有看得到它的人共用（現在是每個人各編一次）；位置量化成 16 位元的相對座標（1～2 cm 精度），比 3 個 f32 省一半 |

| 客戶端 | 最多顯示幾個角色（設定）；遠處的角色用 LOD2 或替身；遠處的動畫降低更新頻率；名牌只畫近的 |
| 存檔 | SQLite（第 5.4 節） |

### 6.7 公開的「官方伺服器」要注意的事

不是法律意見，只是列出規劃書裡已經碰到的限制：
- Tripo 免費方案的產出不能商用、而且是公開的（04-D04）；給其他人玩之前要用付費方案重新產生。
- 跟 Gravity 等作品相似的設計（04 第 4 節）要先處理。
- 遊戲的名稱不能用「Ragnarok」（Gravity 的商標）；`RagnarokChange` 只是專案資料夾的名稱。
- 帳號註冊、防止濫用（02 已經有登入失敗封鎖和 DTLS）、伺服器的 DDoS 防護、玩家管理，都要另外規劃。

## 7. 項目 7：二連擊暴擊時用暴擊動作

### 7.1 查證結果

| 來源（rAthena master） | 內容 |
|---|---|
| `db/re/skill_db.yml` 的 `TF_DOUBLE` | 有 `DamageFlags: Critical: true`，也就是 Renewal 的二連擊**可以暴擊** |
| `db/pre-re/skill_db.yml` 的 `TF_DOUBLE` | 沒有這個旗標：復興前的二連擊不能暴擊 |
| `src/map/battle.cpp` | 判定順序是「完全迴避 → 先判定二連擊 → 再判定暴擊」；二連擊觸發後如果暴擊，攻擊類型是「多段暴擊」，兩段都算暴擊；暴擊必中 |
| 同一個檔案 | 「二連擊的 HIT 加成（每級 ＋1）」只在**二連擊成功觸發的那一下**才有 |

所以 06-D07 寫的「二連擊觸發時不會暴擊」是復興前的規則，跟 06-D01 定的基準（rAthena master 的 Renewal）不一致，是我當時寫錯了。06 第 7.1 節第 4 項「學了二連擊的人 HIT 另加技能等級的百分點」也要改成「二連擊觸發的那一下」。

### 7.2 建議

| 情況 | 動作（05） | 傷害數字（10） |
|---|---|---|
| 一般普攻 | `attack` | 一個白色數字 |
| 暴擊 | `critical` | 一個黃色暴擊數字 |
| 二連擊 | `attack` | 兩個白色數字，間隔 0.15 秒 |
| **二連擊＋暴擊** | **`critical`**（該武器的暴擊動作） | **兩個黃色暴擊數字**，間隔 0.15 秒 |
| Miss | 照 00-S10：普攻動作、目標沒有反應 | Miss（中文版看第 2.4 節） |

- 二連擊在 RO 是短劍才有（另外有 `double_rate` 裝備效果時，徒手以外的武器也會觸發），所以動作是「當下武器的暴擊動作」。
- 02 的 AttackResult：結果用「段數＋是否暴擊」兩個欄位表示，不要用「一般、暴擊、二連擊、二連擊暴擊」這種組合的列舉，之後其他多段攻擊也能用。
