## 2. 決策摘要

## 3. 整體架構

### 3.1 單機模式和多人模式

```text
單機模式（同一個 Godot 程序）

  客戶端（表現層）                                       伺服器（權威模擬）
  輸入 → 指令 ──[位元組]──► 記憶體傳輸 ──[位元組]──► 指令處理 → 模擬 tick
  畫面 ◄── 事件／快照 ◄──[位元組]── 記憶體傳輸 ◄──[位元組]── 事件／快照輸出

多人模式（M9 之後）

  客戶端程序 A ──ENet──┐
  客戶端程序 B ──ENet──┼──► 專用伺服器程序（headless，Linux／Docker）
  客戶端程序 C ──ENet──┘
```

- 客戶端不知道伺服器在同一個程序裡。它只看得到「傳輸介面」，這個介面在單機時是記憶體傳輸，多人時是 ENet。
- 伺服器也不知道客戶端長什麼樣子。它只收指令、送出事件和快照。
- 單機時也照樣把訊息編碼成位元組再解碼。成本在我們的規模下可以忽略，好處是每一種訊息從第一天起都經過真實的編碼路徑，之後接上網路時不會才發現漏洞。

### 3.2 一次 tick 的資料流（以普攻為例）

1. **客戶端**：玩家點怪 → 自動尋路走進射程 → 送出「攻擊意圖（目標）」。
2. **伺服器**：
   1. 檢查射程，留一點容差。
   2. 依 ASPD 用毫秒時間戳排定每一次揮擊。
   3. 每到揮擊時間，就用地圖的亂數產生器判定命中、暴擊或 Miss，並套用傷害。
   4. 送出「攻擊事件」，內容包括攻擊者、目標、揮擊時間、命中時間、結果和傷害值。
3. **客戶端**：播放該武器的普攻或暴擊動作，在命中時間顯示傷害數字。

伺服器負責判定結果，客戶端只負責「播放」。詳細規則在 02（同步）和 06（戰鬥）。

## 4. 分層與依賴規則

### 4.1 各層職責

| 層 | 位置 | 職責 | 可以依賴 | 禁止 |
|---|---|---|---|---|
| shared | `src/shared/` | 資料定義與資料表載入、公式（純函式）、協定編解碼、共用移動程式、常數與列舉 | 只有引擎本身 | 引用 server、client、net；載入任何美術素材 |
| net | `src/net/` | 傳輸介面、記憶體傳輸、ENet 傳輸（M9）、模擬延遲與掉包 | shared | 引用 server、client |
| server | `src/server/` | 世界、地圖實例、實體與元件、各系統（移動、戰鬥、AI、技能、狀態、生成、存檔）、指令處理、事件輸出 | shared、net | 引用 client；載入模型、貼圖、材質、動畫等視覺資源 |
| client | `src/client/` | 連線與時間同步、世界視圖、實體視圖、動畫、裝備外顯、鏡頭、輸入、預測與插值、UI、特效、音效 | shared、net | 引用 server；自己計算會影響結果的數值 |
| boot | `src/boot/` | 入口場景、解析命令列、依模式組裝 client、server、transport | 全部 | — |
| tools | `tools/` | 動作檢視器、自動截圖、烘焙工具、Blender 腳本 | 全部 | 被遊戲程式引用 |
| tests | `tests/` | 各類測試 | 全部 | — |

```text
            boot
          /  |   \
    client  net  server
          \  |   /
          shared
```

上層可以依賴下層。client 和 server 是平行的，不能互相引用。tools 和 tests 不在圖上，它們可以依賴所有層，但遊戲程式不能依賴它們。

### 4.2 客戶端可以算什麼

- **可以算的**：只用來顯示的數值。例如素質視窗預覽「加 1 點 STR 後 ATK 會變多少」，這時呼叫 shared 裡的公式。
- **不可以算的**：任何會影響結果的判定。命中、傷害、掉落、經驗、冷卻是否結束，全部以伺服器送來的資料為準。
- **唯一的例外**：自己角色的移動可以先預測，但最後以伺服器校正為準（細節在 02）。

### 4.3 架構守門測試

headless 自動檢查以下規則，違反任何一條測試就失敗：

| 規則 | 檢查方式 |
|---|---|
| server、shared、net 沒有引用 client | 掃描腳本裡的資源路徑和 client 專屬的類別名稱 |
| client、shared、net 沒有引用 server | 同上，方向相反 |
| server 和 shared 不載入視覺資源 | 掃描載入路徑；檢查所有 logic 場景的相依清單裡沒有模型、貼圖、材質 |
| `.gd` 檔裡沒有中文字元 | 掃描所有腳本。玩家看到的文字一律放在 `locale/<語系>/`（00-S06） |
| `data/` 裡沒有中文字元 | 掃描所有資料檔（00-S06） |
| 檔名和資料夾名稱沒有中文字元 | 掃描整個專案的檔名和資料夾名稱（00-S06） |
| 每個素材都有授權登記 | 對照登記表（格式在 03）；授權代碼、來源、限制標記只能用 04 第 5 節白名單裡的（放寬後也包含 NC、SA，並檢查限制有沒有標記） |
| 顯示文字不混用語言 | 繁中文字裡沒有英文字母（只允許白名單：`docs/glossary.md` 第 6、8 節的 RO 縮寫，例如 `STR`、`ATK`、`HP`、`BOSS`，和參數）；英文文字裡沒有中文字元（03 第 7 節） |
| `data/` 裡沒有顯示文字 | 資料只放 ID、`ro_ref` 和給開發看的英文 `note`，沒有 `name`、`description`（00-S06） |

守門測試本身也要有測試：準備刻意違規的樣本，確認守門測試真的會抓到。

## 5. 執行模式與啟動流程

### 5.1 模式

使用者參數放在 `--` 後面，引擎不會處理這些參數，由程式自己讀取。

| 模式 | 啟動方式 | 會建立的東西 | 何時可用 |
|---|---|---|---|
| 單機（預設） | 直接執行（編輯器按 F5） | 本地伺服器、記憶體傳輸、客戶端；自動登入本機帳號 | M0 骨架、M1 可以玩 |
| 專用伺服器 | `--headless` 加上使用者參數 `--server`；匯出的伺服器版本靠 `dedicated_server` 功能標籤自動判斷 | 伺服器、ENet 監聽 | M9 |
| 連線 | 使用者參數 `--connect=主機:埠` | 客戶端、ENet 連線 | M9 |
| 動作檢視器 | 使用者參數 `--viewer` | 檢視器場景（只有表現層，不需要伺服器） | M3 |
| 自動截圖 | 使用者參數 `--shots=腳本名` | 依截圖腳本載入地圖或檢視器，移動鏡頭到各觀測點，輸出 PNG 和效能紀錄後自動結束 | M0 骨架、M1 起每批都用 |
| 測試 | 用 `--headless` 執行 GUT 的命令列腳本 | 由測試自行建立需要的東西 | M0 |

### 5.2 單機模式的啟動順序

1. 讀取設定（畫質、按鍵、鏡頭，存在使用者資料夾）。
2. 載入遊戲資料表（JSON，格式在 03），並做基本驗證。
3. 建立本地伺服器：載入有玩家所在的地圖的 logic 場景，建立導航地圖，啟動 tick。
4. 建立一對記憶體傳輸端點，一端給伺服器、一端給客戶端。
5. 建立客戶端，連線並握手（版本檢查、本機帳號登入）。
6. 伺服器把角色放到存檔記錄的位置（上次登出的位置），送出進場資料。
7. 客戶端載入該地圖的完整場景（淡入），建立實體視圖，開始接收快照和事件。

## 6. 主迴圈與時間

### 6.1 伺服器 tick

- **頻率**：固定 30 Hz，每個 tick 約 33.3 ms，可以在設定裡調整。
- **推進方式**：把實際經過的時間累加起來，每滿一個 tick 就執行一次。一幀之內最多補跑 N 次，避免越落後越多的惡性循環。
- **主迴圈頻率**：專用伺服器會限制主迴圈頻率，不讓它空轉吃滿 CPU。
- **不綁物理頻率**：單機時伺服器和客戶端共用一個 Godot 程序，物理頻率是全域設定，所以伺服器 tick 由自己控制。

**每個 tick 的處理順序：**
1. 取出並解碼收到的指令，驗證後放進各實體的輸入佇列。
2. 怪物 AI 思考（依各自的思考間隔，錯開執行）。
3. 移動（玩家輸入、怪物路徑）。
4. 處理到期的排程事件（揮擊、詠唱完成、狀態到期等）：時間戳小於等於本 tick 時間的全部處理。
5. 狀態效果和自然回復。
6. 怪物生成與重生。
7. 更新興趣範圍（誰看得到誰）。
8. 輸出：事件（可靠傳送）、快照（不可靠傳送，依快照頻率）。
9. 定期存檔。

### 6.2 事件用時間戳排程

**規則：**
- 揮擊、詠唱、技能後延遲、狀態到期等，一律用伺服器的毫秒時間戳排程。
- 下一次揮擊時間 ＝ 上一次「排定」的時間 ＋ 攻擊間隔，不是「實際處理」的時間 ＋ 攻擊間隔。

**為什麼這樣排：**
- 處理時最多只會晚一個 tick（33 ms），而且延遲不會累積。
- 例如 ASPD 193 時攻擊間隔約 140 ms，它一定照 140 ms 的節奏打，不會被 tick 拖成 167 ms。
- 事件送到客戶端時帶著原本的時間戳，客戶端依自己估算的伺服器時鐘播放，所以動畫節奏跟伺服器一致。

### 6.3 客戶端

- 畫面依螢幕更新率渲染。
- 其他實體依「估算的伺服器時間減去插值延遲」做插值（細節在 02）。
- 自己角色的預測用跟伺服器相同的 30 Hz 步進和同一份移動程式，畫面在兩個預測步之間做插值，所以看起來是平滑的。

## 7. 伺服器端的實體與地圖

### 7.1 實體與元件

- **實體**（RefCounted）：
  - 伺服器指派的整數 ID：在這次執行中不會重複；角色的永久 ID 另外存在存檔裡。
  - 類型：玩家、怪物、掉落物、NPC（M8）。
  - 其他：所在的地圖實例、位置、面向。
- **元件**（RefCounted）：依實體類型組合。

| 元件 | 用途 | 誰有 |
|---|---|---|
| Stats | 素質和衍生數值（依 06） | 玩家、怪物 |
| Movement | 速度、目前的移動意圖或路徑 | 玩家、怪物 |
| Combat | 攻擊意圖、攻擊排程、目標 | 玩家、怪物 |
| SkillCaster | 詠唱、冷卻、技能後延遲 | 玩家、怪物 |
| StatusEffects | 狀態效果清單和到期時間 | 玩家、怪物 |
| AIBrain | 行為狀態機和行為旗標（依 07） | 怪物 |
| Equipment／Inventory | 裝備和物品（物品實例的欄位在 03 第 8.3 節） | 玩家 |
| Perception | 視覺、聽覺、貼身的察覺和警戒（07） | 怪物 |
| Quests | 進行中和完成的任務（M8，03） | 玩家 |
| Appearance | 職業、性別、髮型、髮色、瞳色等（00-A10 預留） | 玩家 |

**不用場景節點的理由：**
- 數百個實體做成節點，負擔比較大。
- 處理順序要由第 6.1 節的固定流程控制，而不是靠節點樹的順序。
- 不需要場景樹，測試就可以直接建立實體。

### 7.2 地圖實例

伺服器的一個地圖實例包含：
- 識別：地圖 ID＋實例編號（01-D07）。第一版每張地圖只有編號 1。
- 地圖定義：來自資料表。
- logic 場景讀出的資料：出生點、傳送點（包含不能過的傳點）、怪物生成區（只有範圍和 `spawn_id`，內容在 `data/spawns/`）、安全區、NPC 位置。
- 視線格網：給怪物的視覺和遠程攻擊的視線檢查（07、08），跟導航網格一樣是烘焙好的資料。
- 一張自己的導航地圖：直接用 NavigationServer3D 建立，不經過 World3D 或 SubViewport，所以不會意外觸發渲染。
- 一個空間格網：用來快速查詢「範圍內有誰」，給興趣範圍、技能範圍、AI 搜尋目標使用。
- 一組亂數產生器（01-D17）。

其他規則：
- 傳送點、安全區的判定是簡單的幾何檢查，不用物理引擎的 Area3D。
- 沒有玩家的地圖會暫停 AI；第一版直接卸載。之後要不要常駐，在 07 決定。

### 7.3 地圖在兩邊各載入什麼

```text
maps/<map_id>/
  map.tscn        客戶端載入：地形、建築、道具、植被、光照、環境
    logic.tscn    放在 map.tscn 裡面；伺服器只載入這個檔案
                  （導航網格、出生點、傳送點、怪物生成區、安全區、NPC 位置）
  sight_grid.res  視線格網（伺服器讀；白模階段由工具一起產生，08）
```

| 項目 | 伺服器 | 客戶端 |
|---|---|---|
| 地形、建築、植被、光照 | 不載入 | 載入 |
| 導航網格 | 載入（自己的導航地圖） | 載入（隨 logic 場景放進客戶端世界） |
| 視線格網 | 載入 | 不需要（除錯顯示時才讀） |
| 傳送點、生成區等標記 | 讀成資料 | 用來顯示傳送門特效、除錯顯示 |
| 地形外掛（Terrain3D） | 不需要 | 需要 |

規則：logic 場景不能引用任何視覺資源，由守門測試檢查（第 4.3 節）。這樣伺服器在匯出時可以剝除視覺資源，也不需要地形外掛。

### 7.4 移動

- 所有角色都在導航網格上移動：沒有跳躍、角色之間互相穿透，跟 RO 一樣。
- 每一步都用小步長前進，並貼齊導航網格的表面；碰到網格邊緣時沿著邊緣滑動。
- 這份程式放在 shared。伺服器用它推進和驗證；客戶端用它預測自己的角色、讓自動追擊時的自動尋路走路。
- 伺服器不使用物理碰撞體，所以伺服器端的 3D 物理完全不用。
- 客戶端只在兩個地方用物理：鏡頭碰牆偵測（09）、滑鼠點選實體（09）。

### 7.5 定義、狀態、衍生值

| 層 | 內容（例子） | 誰寫 | 生命週期 | 放在哪裡 |
|---|---|---|---|---|
| 定義（唯讀） | 職業、技能、物品、怪物、規則常數、生成表、附加能力的池、任務 | 開發者（JSON） | 啟動時載入，執行中不變 | `data/`（算進資料雜湊） |
| 狀態（動態） | 角色、這一把劍（精煉、卡片、附加能力）、場上的怪物、狀態效果、冷卻、地上的掉落物、任務進度 | 伺服器 | 執行中會變；需要保留的才存檔 | 伺服器記憶體的元件、存檔 |
| 衍生值（快取） | 素質加總、ATK、ASPD、移動速度 | 伺服器依「定義＋狀態」算出 | 依賴的東西變了才重算（髒旗標） | 記憶體；不存檔、不相信客戶端 |

規則：
1. 狀態只用 ID（存檔、網路）或 u16 索引（執行中、網路）指向定義，不複製定義的數值。改了平衡數值，舊角色和舊物品馬上套用新值。
2. 定義載入後凍結：`Dictionary` 和 `Array` 用 `make_read_only()`，不小心寫入時直接報錯。
3. 衍生值不存檔。存檔只放狀態（03 第 8 節）。
4. 所有效果來源（裝備、卡片、附加能力、狀態效果、被動技能）先收集成「修正值清單」，再一次算出衍生值，用同一套有名字的效果類型（03、06）。

## 10. 程式規範

| 規則 | 內容 |
|---|---|
| 語言 | 程式碼、註解、log 一律英文。玩家看到的文字放 `locale/<語系>/`，程式用鍵取（00-S06、03 第 7 節）。 |

## 11. 測試與驗證

### 11.1 測試種類

| 種類 | 內容 | 執行方式 | 什麼時候跑 |
|---|---|---|---|
| 單元 | 公式、資料驗證、協定編解碼、工具函式 | headless GUT | 每次 commit 前 |
| 整合 | 同一個程序裡跑 1 個伺服器加多個客戶端（記憶體傳輸，可以加模擬延遲），測移動同步、換圖、斷線 | headless GUT | 每次 commit 前 |
| 冒煙 | 依序載入每張地圖、每個角色和怪物場景，跑 N 幀，不能出現任何錯誤；檢查每個角色的動作清單完整 | headless | 每批驗收 |
| 守門 | 第 4.3 節的所有規則 | headless | 每次 commit 前 |
| 自動截圖 | 各觀測點截圖，並記錄 FPS、幀時間、draw call、三角形數、顯示記憶體 | 非 headless（需要 GPU） | 每批驗收 |
| 人工 | 你在 Godot 按 F5 看畫面，依截圖清單回報 | — | 每批驗收 |

### 11.2 指令腳本（M0 建立，這裡只描述用途）

| 腳本 | 用途 |
|---|---|
| `tools/scripts/check.ps1` | 先讓 Godot 匯入所有資源，再用 headless 跑全部的單元、整合、冒煙、守門測試，回傳成功或失敗。每次 commit 前都要跑。 |
| `tools/scripts/shots.ps1` | 用自動截圖模式跑指定的截圖腳本，輸出到 `artifacts/`。 |
| `tools/scripts/inbox.ps1` | 呼叫 Blender 處理 `_inbox`（流程在 04）。 |
| `tools/scripts/server.ps1` | 在本機啟動 headless 專用伺服器（M9 之後才有）。 |

### 11.3 自動截圖模式

- **目的**：在請你截圖之前，我先自己看過畫面。
- **流程**：每張地圖定義幾個「觀測點」（位置和鏡頭角度，在 08 定義）。截圖模式依序把鏡頭移過去，等畫面穩定後存成 PNG，同時記錄效能數據。
- **檢視器截圖**：動作檢視器也可以用同樣的方式，輸出每個動作的關鍵影格。
- **動畫序列**：需要連續影格時，用 Godot 內建的 Movie Maker 模式，以固定幀率輸出 PNG 序列，畫面不受機器速度影響。
- **輸出位置**：截圖和效能紀錄都放在 `artifacts/`，不提交到 Git。

## 14. 效能預算

以下數字都是暫定，M1 實測後修正。

| 項目 | 預算 |
|---|---|
| 目標 | RTX 4060（8 GB）上 1080p、「高」畫質、60 fps（00-S15） |
| 幀時間 | 平均 ≤ 16.6 ms，最慢 1% 的幀 ≤ 20 ms |
| GPU | ≤ 12 ms |
| 客戶端主執行緒 | ≤ 8 ms |
| draw call（不含陰影） | ≤ 2,000 |
| 畫面內三角形 | ≤ 400 萬 |
| 顯示記憶體 | ≤ 6 GB（4060 共 8 GB） |
| 伺服器 tick | 同時 20 名玩家、單張地圖約 200 隻怪物時，每個 tick ≤ 10 ms（M9 另外用壓力測試量 50、100 人，02） |
| 換圖載入 | ≤ 5 秒（SSD） |

**量測方式**：自動截圖模式在各觀測點關閉垂直同步，記錄 Godot 內建的效能監視數據。需要深入分析時用 Godot 的分析器。

**畫質等級**：

| 等級 | 用途 | 驗收 |
|---|---|---|
| 高 | 平常遊玩 | 上表的預算（原生 1080p） |
| 電影 | 截圖、展示：更高的全域光照、體積霧、陰影、植被距離 | 只量測、記錄，不要求達標 |
| 中、低 | 之後給比較弱的電腦 | 之後再定 |

- Godot 內建的 FSR 2 放大可以在設定裡開啟，但驗收一律用原生 1080p。
- 畫面的精緻度以 Road to Vostok 為目標（00-S17）；效能不夠時先用 LOD、可見距離、遮擋剔除調整（08、04），不先降低目標。

**渲染驅動**：
- 根據 Godot 4.6 的相關報導，4.6 起在 Windows 上建立的新專案預設使用 D3D12（Vulkan 還是可以選）。environment-setup.md 寫的是 Vulkan。M0 建專案時會直接看專案設定確認。
- M0 先用新專案的預設值建立專案，再拿同一個測試場景比較兩種驅動。比較的項目有平均幀時間、最慢 1% 的幀時間、第一次載入著色器時的卡頓。
- 比較後挑表現好的。如果結果跟 environment-setup.md 不同，我會提出修改建議，不會直接改。

**物理引擎**：Godot 4.6 起，新專案的 3D 物理預設是 Jolt。客戶端只用物理做鏡頭碰撞和滑鼠點選，伺服器完全不用，所以照預設即可。

## 15. log、錯誤與隨機數

- **log 等級與分類**：
  - 等級分成 DEBUG、INFO、WARN、ERROR。
  - 分類例如 net、combat、ai、asset、map。
- **單機模式**：每行 log 加上 `[SV]` 或 `[CL]` 前綴，分辨是伺服器還是客戶端。
- **log 輸出位置**：
  - 單機和客戶端：主控台加上使用者資料夾裡的 log 檔。
  - 專用伺服器：輸出到標準輸出，並開啟「每次輸出立即寫出」，方便 Docker 收集。
- **測試**：冒煙和整合測試會攔截錯誤輸出，只要出現錯誤就判定失敗。
- **隨機數**：
  - 命中、暴擊、二連擊、掉落、附加能力等會影響結果的隨機數，全部由伺服器所在地圖實例的亂數產生器產生。
  - 測試可以指定種子，讓結果可以重現。
  - 客戶端只用隨機數做外觀變化，例如待機小動作要播哪一個、粒子特效的變化。

## 18. 風險與備案

| 風險 | 影響 | 備案 |
|---|---|---|
| Terrain3D 在 4.7 上不能用 | 草原地形要換做法 | M1 先做技術驗證；不行就改用 Blender 產生的高度圖網格（細節在 08） |
| 在導航網格上移動的邊界情況（貼邊、樓梯高度） | 角色卡住或抖動 | M1 寫整合測試涵蓋；細節在 02 和 09 |
| GDScript 在伺服器端的效能 | 怪物很多、人很多時 tick 變慢 | 20 人應該沒問題。M9 用壓力測試量 50、100 人；熱點（快照編碼、興趣範圍）不夠快時再考慮改寫成 C++ 的 GDExtension，先量測再提出，由你決定 |
| SQLite 要用 GDExtension | 外掛和 Godot 版本不相容 | 用之前查證版本（00-S09）；存檔介面（`AccountStore`）不變，換實作就好 |
| 單機模式中伺服器多載入一份導航資料 | 記憶體多用一點 | 導航資料很小，可以接受 |
| 外掛更新後不相容 | 編譯或執行失敗 | 版本固定，升級另開分支 |
| LFS 容量（之後設遠端時） | 推不上去 | 選 LFS 容量夠的遠端，見第 13.5 節 |

## 19. 與 RO 原制不同之處（待檢視）

| 項目 | RO 原制 | 本專案 | 理由 |
|---|---|---|---|
| 移動 | 格子地圖，8 個方向，點地移動 | 在導航網格上連續移動，用 WASD 操作 | 00-S02 選了 WASD，加上寫實 3D 的需要 |
| 距離和速度的單位 | 格子、每格毫秒 | 資料一律用公尺、公尺／秒（RO 的 1 格 ＝ 1 公尺，換算表在 06 第 3 節） | 00-S14；3D 要表達身體大小、高度差、扇形範圍 |
| 地圖實例 | 一張地圖一份 | 地圖 ID＋實例編號，之後可以分流 | 為了之後的分流和私人房間（02） |

除了上表，本文件其他部分沒有偏離 RO 的地方。沒有跳躍、角色互相穿透，都跟 RO 一致。
